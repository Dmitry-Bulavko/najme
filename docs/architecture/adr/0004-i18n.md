# ADR-0004: Internationalization

- Status: Accepted
- Date: 2026-09-28

## Context

Target market is Montenegro with locals, Russian-speaking and Turkish residents, and tourists. The UI
must be available in four languages from day one, on web and mobile, and notifications must be
localized.

## Decision

### Locales

| Code | Label shown in UI   | BCP-47 for `Intl` | Notes                                    |
| ---- | ------------------- | ----------------- | ---------------------------------------- |
| `en` | English             | `en`              | **Default and fallback**                 |
| `me` | Crnogorski / Srpski | `sr-Latn-ME`      | Latin script; covers Montenegrin/Serbian |
| `ru` | Русский             | `ru`              |                                          |
| `tr` | Türkçe              | `tr`              |                                          |

`me` is our internal code. Use the BCP-47 tag for date/number/plural formatting because CLDR data for
`cnr` is incomplete.

### Resolution order

1. Explicit user choice (stored in the user profile when signed in; cookie/storage otherwise).
2. Device / browser languages in order (`Accept-Language`, `expo-localization`), mapped:
   `sr*`, `cnr*`, `bs*`, `hr*`, `sh*` → `me`; `ru*`, `uk*`, `be*` → `ru`; `tr*` → `tr`; `en*` → `en`.
3. Fallback `en`.

The resolver lives in `packages/i18n` and is shared by web, mobile and the API (for notifications).

### Catalogs

- Message catalogs live in `packages/i18n` as one JSON file per locale per namespace, using ICU
  message syntax (plurals, select).
- `en` is the source of truth; a test fails if any locale is missing a key or has extra keys.
- Agents add strings in **all four** locales in the same PR. Machine-quality translations are
  acceptable for now; mark uncertain ones in the PR description for human review.

### Content

- Platform content (categories, notification templates) is stored with translations per locale.
- Business-entered content (service names, descriptions) is stored as entered, in one language (see
  open question Q7).
- Dates/times are always displayed in the **business timezone** with the user's locale formatting.

## Consequences

- No hardcoded user-facing strings anywhere — reviewers treat them as blockers.
- Adding a fifth locale = new catalog files + one entry in the locale list.
